# Траблшутінг etcd після зміни топології (beelinkeqr5 → Syhiv17, 192.168.1.19)

Документ описує аналіз та план дій після зміни топології згідно з діаграмою **Syhiv VPN-2.pdf**.

---

## 1. Поточна топологія (з діаграми Syhiv VPN-2.pdf)

| Локація / Роутер | Нода k3s | IP підмережі | Примітка |
| ------------------ | ---------- | -------------- | ---------- |
| **VRN625** (Vern625) | macmini7 (k3s master) | 192.168.2.19/24, gw 192.168.2.1 | Без змін |
| **Syhiv17** | beelinkeqr5 (k3s master) | **192.168.1.19/24**, gw 192.168.1.1 | **Нова локація та нова адреса** |
| OCI VLAN | master-node, work-node, sharedata | 10.0.10.x, WG-тунелі | Без змін |

**Що змінилося:** нода **beelinkeqr5** перенесена на локацію роутера **Syhiv17** і отримала адресу **192.168.1.19** (раніше була в мережі 192.168.2.x, наприклад 192.168.2.95 або 192.168.2.155).

---

## 2. Чому etcd працює некоректно

etcd зберігає **список членів кластера (member list)** з **peer URL** для кожної ноди. Peer URL — це адреса, за якою інші ноди з’єднуються з цим членом (порт **2380**).

- **До зміни:** beelinkeqr5 була зареєстрована в etcd з peer URL типу `https://192.168.2.95:2380` (або 192.168.2.155).
- **Після переїзду:** фізична нода beelinkeqr5 має IP **192.168.1.19**, але в etcd досі записано старий URL.

Наслідки:

1. **macmini7** (та інші control-plane) намагаються з’єднатися з beelinkeqr5 за **старим IP** → з’єднання таймаутять або connection refused.
2. **beelinkeqr5** при старті k3s бачить у кластері запис «beelinkeqr5 = старий_IP:2380», а локально має 192.168.1.19 → помилка типу **"this server is not a member of the etcd cluster"** або **"expect: ... [https://192.168.1.19:2380]"**.
3. Кворум etcd (при 2 нодах потрібні 2 з 2) не досягається → **немає лідера** → API повертає `ServiceUnavailable`, `etcdserver: no leader`.

## 3. План траблшутінгу

### Фаза A: Діагностика (переконатися, що причина саме в зміні IP)

| Крок | Де виконувати | Дія | Очікуваний результат / інтерпретація |
| ------ | ---------------- | ----- | -------------------------------------- |
| A.1 | Будь-яка нода з kubectl | `kubectl get nodes -o wide` | beelinkeqr5 може бути NotReady або взагалі не в списку; якщо в списку — перевірити INTERNAL-IP (має бути 192.168.1.19 після виправлення). |
| A.2 | macmini7 (192.168.2.19) | `sudo k3s etcdctl member list` | Побачити список членів etcd. Знайти рядок з **beelinkeqr5** і перевірити **peer URL**: якщо там старий IP (наприклад 192.168.2.95 або 192.168.2.155), а не 192.168.1.19 — причина підтверджена. |
| A.3 | macmini7 | `journalctl -u k3s -n 100 --no-pager` або `sudo k3s server --help` | У логах шукати: "not a member of the etcd cluster", "expect: ... 192.168.1.19", "no leader", "remote-peer-id ... EOF". |
| A.4 | beelinkeqr5 (192.168.1.19) | `ip -4 addr show` | Переконатися, що поточна адреса ноди дійсно **192.168.1.19**. |
| A.5 | macmini7 → beelinkeqr5 | `nc -zv 192.168.1.19 2380` та `nc -zv 192.168.1.19 2379` | Після виправлення etcd порти мають бути доступні. До виправлення — перевірка мережевої досяжності (firewall, маршрути Syhiv17 ↔ Vern625). |

Якщо в A.2 peer URL для beelinkeqr5 — старий IP, а поточна адреса beelinkeqr5 — 192.168.1.19, переходимо до фази B.

---

### Фаза B: Виправлення etcd (оновлення peer URL)

| Крок | Де виконувати | Дія |
| ------ | ---------------- | ----- |
| B.1 | **macmini7** (або master-node, якщо він у тому ж кластері й має кворум) | Отримати MEMBER_ID: `sudo k3s etcdctl member list` → знайти ID члена з peer URL зі старим IP beelinkeqr5. |
| B.2 | macmini7 | Оновити peer URL: `sudo k3s etcdctl member update MEMBER_ID --peer-urls="https://192.168.1.19:2380"` |
| B.3 | macmini7 | Перевірити: `sudo k3s etcdctl member list` — у рядку beelinkeqr5 має бути `https://192.168.1.19:2380`. |
| B.4 | **beelinkeqr5** | Перезапустити k3s: `sudo systemctl restart k3s` та `sudo systemctl status k3s`. |
| B.5 | Будь-яка нода | `kubectl get nodes -o wide` — beelinkeqr5 має бути Ready з INTERNAL-IP 192.168.1.19. |

Детальний покроковий опис з прикладами команд — у **[FIX_ETCD_MEMBER_IP_CHANGE.md](./FIX_ETCD_MEMBER_IP_CHANGE.md)** (там вказано нову адресу 192.168.1.19).

---

### Фаза C: Після відновлення кластера

| Крок | Дія |
| ------ | ---- |
| C.1 | Оновити конфіги, де жорстко прописані IP beelinkeqr5: Prometheus (kubernetes-nodes, node-exporter) — замінити 192.168.2.95 на **192.168.1.19**; документацію (FIX_PORTAINER, тощо) — за потреби. |
| C.2 | Перевірити маршрути та firewall між 192.168.1.0/24 (Syhiv17) та 192.168.2.0/24 (Vern625): порти 2379, 2380, 6443 мають бути доступні між macmini7 і beelinkeqr5. |
| C.3 | Якщо використовується **tls-san**: на beelinkeqr5 у k3s додати `--tls-san 192.168.1.19`, щоб сертифікати API/etcd включали нову адресу. |

---

## 4. Короткий чеклист

- [ ] Діагностика: `k3s etcdctl member list` на macmini7 — перевірити peer URL для beelinkeqr5.
- [ ] Оновлення: `k3s etcdctl member update MEMBER_ID --peer-urls="https://192.168.1.19:2380"` на macmini7.
- [ ] Перезапуск k3s на beelinkeqr5.
- [ ] Перевірка: `kubectl get nodes` — beelinkeqr5 Ready, 192.168.1.19.
- [ ] Оновити Prometheus configmap: 192.168.2.95 → 192.168.1.19 для beelinkeqr5.
- [ ] Перевірити зв’язність та firewall між 192.168.1.19 та 192.168.2.19 (2379, 2380, 6443).

Після виконання цих кроків etcd має коректно формувати кворум, а beelinkeqr5 — працювати як control-plane на Syhiv17 з адресою 192.168.1.19.
