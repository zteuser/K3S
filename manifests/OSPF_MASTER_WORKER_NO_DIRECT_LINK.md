# OSPF: лінк master-node ↔ work-node (OCI) та відсутність WG-тунелю

У документі пояснено: **OSPF-сесія між Amper master та Amper worker встановлена** (напряму по OCI). Між цими двома нодами **немає лише окремого WireGuard-тунелю** — це не заважає OSPF.

---

## 1. Поточний стан (згідно з **Syhiv OSPF.pdf**)

У OSPF беруть участь **чотири вузли**: Amper master, Amper worker, Syhiv17, VRN625. Ноди macmini7 та beelinkeqr5 мають WireGuard-тунелі до Amper, але **не запускають OSPF** — маршрутизація до них через роутери.

**OSPF-сусіди (з виводу `sh ip ospf neighbor` у PDF):**

- **master-node:**  
  - **10.0.10.20** — **Full** по **enp0s6:10.0.10.10** (пряма OSPF-сесія з worker по OCI VLAN 10.0.10.0/24);  
  - 192.168.1.1 (Syhiv17) по wg0; 192.168.2.1 (VRN625) по wg1.
- **work-node:**  
  - **10.0.10.10** — **Full** по **enp0s6:10.0.10.20** (пряма OSPF-сесія з master по OCI);  
  - 192.168.1.1 (Syhiv17) по wg0; 192.168.2.1 (VRN625) по wg1.

Тобто **OSPF session між Amper master та Amper worker є і встановлена напряму по інтерфейсу enp0s6** (OCI). Між двома OCI-нодами **немає окремого WireGuard-тунелю** — вони знаходяться в одній OCI VLAN, тому для OSPF використовується саме цей прямий лінк (enp0s6).

---

## 2. Чи це проблема для повного mesh?

**Ні.** Для повної mesh-схеми достатньо, щоб:

1. Кожна нода могла **досягти** кожної (маршрути є).
2. OSPF **збирає повну LSDB** у Area 0 і всі маршрути розраховуються коректно.

### 2.1 OSPF між master і worker

**Пряма OSPF-сесія master ↔ worker існує** — по OCI (enp0s6), як видно в **Syhiv OSPF.pdf** (перший сусід у списку на обох нодах, інтерфейс enp0s6, стан Full).

- master-node і work-node є **прямими OSPF-сусідами** по мережі 10.0.10.0/24 (enp0s6).
- Додатково обидва мають сусідів Syhiv17 та VRN625 по WireGuard (wg0, wg1).
- LSA вони обмінюються і напряму (по OCI), і через роутери; маршрути до 10.0.10.x та 192.168.100.0/24, 192.168.200.0/24 будуються коректно.

Окремий **WireGuard**-тунель між двома OCI-нодами для OSPF **не потрібен** — прямий лінк вже є (OCI VLAN).

### 2.2 Граф зв’язності (4 вузли OSPF)

```
                    Syhiv17 (192.168.1.1)
                   /                    \
                  /                      \
    master-node ---- OCI (10.0.10.0/24) ---- work-node
                  \                      /
                   \                    /
                    VRN625 (192.168.2.1)
```

Master і worker з’єднані **напряму по OCI** (enp0s6) і додатково через Syhiv17 та VRN625 по WG. Граф **зв’язаний**; macmini7 та beelinkeqr5 не в OSPF — до них маршрути через роутери.

### 2.3 Як йде трафік master ↔ worker

Трафік між 10.0.10.10 і 10.0.10.20 може йти **по OCI** (enp0s6) або через роутери:

- master → enp0s6 (OCI) → worker, або  
- master → wg0 → Syhiv17 → wg0 → worker, або  
- master → wg1 → VRN625 → wg1 → worker.

macmini7 та beelinkeqr5 не в OSPF; якщо трафік йде через них по WG (wg2/wg3), це на рівні IP/маршрутизації, а не OSPF.

## 3. Висновок

| Питання | Відповідь |
|--------|-----------|
| Чи встановлена OSPF-сесія між master і worker? | **Так.** Вона встановлена **напряму по OCI** (enp0s6), стан Full — див. **Syhiv OSPF.pdf** (вивід `sh ip ospf neighbor`). |
| Чи потрібен окремий WG-тунель master ↔ worker для OSPF? | **Ні.** Прямий OSPF-лінк уже є по OCI; додатково обидва мають сусідів Syhiv17 та VRN625 по WG. |
| Чи забезпечується повна mesh? | **Так.** Усі **чотири** вузли OSPF (master, worker, Syhiv17, VRN625) в Area 0 мають однакову LSDB і коректні маршрути. macmini7 та beelinkeqr5 не в OSPF; до них маршрутизація через роутери. Візуалізація — **Syhiv OSPF.pdf**. |

Додавання **окремого WG-тунелю** між двома OCI-нодами (master ↔ worker) могло б дати запасний шлях поверх WireGuard, але для OSPF це **не обов’язково** — пряма OSPF-сесія вже є по OCI (enp0s6). Поточна схема достатня.
