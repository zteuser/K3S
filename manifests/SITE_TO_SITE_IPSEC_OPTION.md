# Варіант переходу на site-to-site IPsec (замість WireGuard)

Документ описує, що означає перехід з WireGuard на **site-to-site IPsec** між роутерами (VRN625, Syhiv17) та Amper (OCI), які переваги це дає для кластера k3s, і які кроки потрібні.

---

## 0. Обмеження: роутери за CGNAT

**VRN625 та Syhiv17 не мають виділеної публічної інтернет-адреси і знаходяться за CGNAT.**

- За CGNAT роутери лише **ініціюють** вихідні з’єднання; зовнішній сервер (Amper) **не може** до них підключитися за сталим публічним IP.
- Класичний **site-to-site IPsec** розрахований на сторони з публічними (або хоча б стабільними) IP; коли обидва “сайти” за CGNAT або один за CGNAT без виділеної IP, налаштування IPsec стає непрацездатним або непередбачуваним (наприклад, два роутери виглядають з інтернету як одна CGNAT-адреса — розрізнити два тунелі на Amper неможливо).
- **WireGuard** у поточній схемі саме для цього і підходить: роутери є **клієнтами** і самі підключаються до Amper (сервера з публічною IP). Трафік завжди ініціюється з боку роутера → CGNAT не заважає.

**Висновок:** при роутерах за CGNAT варіант site-to-site IPsec **не застосовується**. Залишаємо WireGuard і використовуємо [PLAN_NETWORK_AND_REBUILD_CONTROL_PLANE.md](PLAN_NETWORK_AND_REBUILD_CONTROL_PLANE.md) з **tls-san** для тунельних IP. Далі в документі опис IPsec збережено для випадку, коли в майбутньому з’явиться виділена публічна IP для VRN625/Syhiv17.

---

## 1. Що таке site-to-site IPsec у вашій топології

**Поточна схема (WireGuard):** VRN625 і Syhiv17 — клієнти WG, підключаються до Amper master/worker (WG-сервери). Трафік з LAN (192.168.2.x, 192.168.1.x) йде в тунель; на роутерах за замовчуванням **MASQUERADE** → приймач бачить source IP тунелю (192.168.100.6, 192.168.100.2 тощо), тому в etcd потрібні **tls-san** з тунельними IP.

**Site-to-site IPsec:** тунель між **двома шлюзами** (наприклад, VRN625 ↔ Amper, Syhiv17 ↔ Amper). Зазвичай налаштовується як **routed** (policy-based або route-based): кожна сторона оголошує свої локальні мережі та віддалені мережі; трафік між цими мережами йде в IPsec без **NAT** — source IP зберігається (192.168.2.19, 192.168.1.19, 10.0.10.10). Тоді etcd бачить справжні LAN-адреси хостів, і в **tls-san** достатньо лише цих адрес (без тунельних 192.168.100.x).

## 2. Порівняння WireGuard і site-to-site IPsec

| Критерій | WireGuard (поточний стан) | Site-to-site IPsec |
|----------|---------------------------|---------------------|
| **NAT на роутерах** | MASQUERADE на wgclt+ (Unifi за замовчуванням) → source IP тунелю | Типово **без NAT** для трафіку в тунель → source IP = LAN хоста |
| **tls-san для etcd** | Потрібні тунельні IP (192.168.100.2, 192.168.100.6 тощо) + LAN | Достатньо лише LAN (10.0.10.10, 192.168.2.19, 192.168.1.19) |
| **Складність налаштування** | Нижча (WG-конфіг, ключі) | Вища (IKE Phase 1/2, DH, шифри, PSK або сертифікати) |
| **Підтримка на Unifi** | WireGuard Client (клієнт до зовнішнього сервера) | Site-to-Site IPsec (IKEv1/IKEv2) до іншого шлюза |
| **Підтримка на Amper (Linux)** | wg0/wg1, скрипти NAT | strongswan або libreswan (IPsec responder/initiator) |
| **Топологія** | 2 роутери → 2 Amper (master + worker), 4 тунелі | Можна: 2 роутери → 1 або 2 точки на Amper (наприклад, один strongswan на master з двома conn для VRN625 і Syhiv17) |
| **Надійність/стандарти** | Нова протокол, простий | IPsec/IKE — стандарт, широка підтримка, часто вимагається в корпоративних середовищах |

## 3. Що дає перехід на IPsec для k3s

1. **Спрощення tls-san:** etcd бачить 192.168.2.19, 192.168.1.19, 10.0.10.10 — тунельні IP не з’являються в трафіку. У `/etc/rancher/k3s/config.yaml` можна не додавати 192.168.100.x, 192.168.200.x.
2. **Менше залежності від NAT:** не потрібно обходити MASQUERADE правилами iptables на роутерах (див. DISABLE_NAT_ON_WIREGUARD_ROUTERS.md).
3. **Один тип VPN:** якщо потрібна сумісність з іншими site-to-site (партнери, офіси), IPsec часто вже є на шлюзах.

## 4. Що потрібно змінити технічно

### 4.1 На роутерах (VRN625, Syhiv17) — Unifi

- У **Unifi Network** → **Settings** → **VPN** (або **Gateways** → вибрати шлюз → **VPN**): створити **Site-to-Site IPsec** (не WireGuard Client).
- Параметри: **Remote IP/Hostname** = публічна IP Amper (141.144.254.42 для master, або один endpoint для всього Amper). **Local subnets** = 192.168.2.0/24 (VRN625) або 192.168.1.0/24 (Syhiv17). **Remote subnets** = 10.0.10.0/24, 192.168.1.0/24 (для VRN625) або 10.0.10.0/24, 192.168.2.0/24 (для Syhiv17).
- **Authentication:** Pre-Shared Key (PSK) або сертифікати, залежно від того, що підтримує Unifi і strongswan.
- **IKE version:** IKEv2 (рекомендовано) або IKEv1; алгоритми (AES, SHA, DH group) мають збігатися з Amper.

Деталі: [UniFi Gateway - Site-to-Site IPsec with Third-Party Gateways](https://help.ui.com/hc/en-us/articles/7983431932439).

### 4.2 На Amper (Linux)

- Встановити **strongswan** (або libreswan): `apt install strongswan`.
- Налаштувати **ipsec.conf** та **ipsec.secrets**: один conn для кожного роутера (VRN625, Syhiv17) або один conn з двома right subnets. **Left** = Amper (10.0.10.10 або публічна IP), **right** = публічна IP VRN625 та Syhiv17; **leftsubnet** = 10.0.10.0/24, **rightsubnet** = 192.168.2.0/24 та 192.168.1.0/24.
- **Не** вмикати NAT для трафіку в IPsec (strongswan за замовчуванням не робить MASQUERADE для site-to-site).
- Firewall: дозволити UDP 500 (IKE), UDP 4500 (NAT-T), протокол ESP.

Якщо зараз два окремі Amper (master і worker) — потрібно вирішити, хто є IPsec-шлюзом: один хост (наприклад, master) з маршрутами до 10.0.10.0/24 та до worker, або окремі conn на кожному Amper (складніша схема).

### 4.3 Маршрути

- На VRN625/Syhiv17 через Unifi задаються **remote subnets** — маршрути в тунель з’являються автоматично.
- На Amper: маршрути до 192.168.2.0/24 та 192.168.1.0/24 через strongswan (часто автоматично через **left|rightsubnet**).

### 4.4 k3s після переходу

- Peer URL etcd залишаються **тільки LAN**: 10.0.10.10, 192.168.2.19, 192.168.1.19 (як у PLAN, розділ 5).
- **tls-san:** достатньо цих самих адрес; тунельні 192.168.100.x, 192.168.200.x **не потрібні**, якщо через IPsec source IP не змінюється.
- Перебудова control plane (якщо вже планується) може бути зроблена вже з розрахунком на IPsec або спочатку на WG з правильними tls-san, а потім міграція VPN.

## 5. Міграція: варіанти

| Варіант | Опис |
|--------|------|
| **A. Паралельно** | Підняти IPsec поруч із WireGuard; перемкнути маршрути (на роутерах змінити default або статичні маршрути до 10.0.10.0/24, 192.168.x на IPsec замість WG); перевірити etcd/k3s; потім вимкнути WG. |
| **B. Повна заміна** | Зупинити WG на роутерах і Amper, налаштувати IPsec, перезапустити k3s з оновленим config.yaml (без тунельних tls-san). Ризик: простій поки IPsec не запрацює. |
| **C. Залишити WireGuard** | Не мігрувати; використовувати поточну схему з **tls-san** для тунельних IP (PLAN_NETWORK_AND_REBUILD_CONTROL_PLANE.md). Найменше змін. |

---

## 6. Висновок

- **Site-to-site IPsec** дає трафік без NAT через тунель → etcd бачить справжні LAN IP → **tls-san** без тунельних адрес.
- Ціна: складніша налаштування (IKE/ESP, strongswan на Amper, узгодження параметрів з Unifi) і міграція з поточного WireGuard.
- **При роутерах за CGNAT** (як VRN625 і Syhiv17) site-to-site IPsec **не підходить** — немає виділеної публічної IP для прийому з’єднань. Єдиний практичний варіант — **WireGuard** (роутери як клієнти до Amper) + **tls-san** для тунельних IP (PLAN).
- Якщо мета — лише стабільний etcd, достатньо **залишити WireGuard** і використовувати правильні **tls-san** (PLAN). Якщо в майбутньому з’явиться виділена публічна IP для роутерів і потрібна саме IPsec — можна планувати міграцію за варіантом A або B (див. PLAN_FULL_REPLACEMENT_WG_TO_IPSEC.md).
