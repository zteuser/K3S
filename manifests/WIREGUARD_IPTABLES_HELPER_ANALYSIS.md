# Аналіз iptables helper-скриптів WireGuard (Amper master/work-node)

Скрипти в `/etc/wireguard/helper/` виконуються при піднятті/знятті інтерфейсів wg0–wg3 (PostUp/PostDown у конфігах). Нижче — можливі помилки та рекомендації.

---

## 1. Що роблять скрипти (коротко)

| Інтерфейс | NAT (MASQUERADE) | INPUT | FORWARD |
|-----------|------------------|--------|---------|
| **wg0** | Так (SUB_NET → enp0s6) | wg0, UDP port | enp0s6↔wg0, wg0↔wg1 |
| **wg1** | Так (SUB_NET → enp0s6) | wg1, UDP port | enp0s6↔wg1, wg1↔wg0 |
| **wg2** | **Ні** (master і work) | wg2, UDP port | enp0s6↔wg2, wg2↔wg3 |
| **wg3** | **Ні** (master і work; на work рядок закоментований) | wg3, UDP port | enp0s6↔wg3, wg3↔wg2 |

Тобто NAT лише для тунелів до роутерів (wg0, wg1); для тунелів до нод (wg2, wg3) NAT немає — source IP зберігаються (192.168.2.19, 192.168.1.19), що потрібно для etcd/k3s.

---

## 2. Критична проблема: немає FORWARD між wg0/wg1 та wg2/wg3

**Симптом:** Трафік між «блоком» роутерів (wg0, wg1) і «блоком» нод (wg2, wg3) може не проходити.

Зараз є лише:

- **wg0 ↔ wg1** (роутери між собою та з інтернетом через NAT)
- **wg2 ↔ wg3** (macmini7 ↔ beelinkeqr5 через Amper)
- **кожен wgX ↔ enp0s6**

Немає правил на кшталт:

- `-i wg0 -o wg2`, `-i wg2 -o wg0`
- `-i wg0 -o wg3`, `-i wg3 -o wg0`
- `-i wg1 -o wg2`, `-i wg2 -o wg1`
- `-i wg1 -o wg3`, `-i wg3 -o wg1`

Якщо політика FORWARD за замовчуванням **DROP**, то:

- Syhiv17 (wg0) ↔ macmini7 (wg2) або beelinkeqr5 (wg3) — **drop**
- VRN625 (wg1) ↔ macmini7 (wg2) або beelinkeqr5 (wg3) — **drop**

Це ламає повний mesh і OSPF між усіма пристроями.

**Рекомендація:** Додати на **master-node** і **work-node** у кожен add-скрипт (або в окремі правила після підняття всіх інтерфейсів) FORWARD для пар:

- wg0 ↔ wg2, wg0 ↔ wg3  
- wg1 ↔ wg2, wg1 ↔ wg3  

Приклад для **add-nat-routing-wg2.sh** (master):

```bash
# Існуючі правила...
$IPT -I FORWARD 1 -i $WG2_FACE -o $WG3_FACE -j ACCEPT

# Додати: wg2 ↔ wg0, wg2 ↔ wg1
$IPT -I FORWARD 1 -i $WG2_FACE -o $WG0_FACE -j ACCEPT
$IPT -I FORWARD 1 -i $WG0_FACE -o $WG2_FACE -j ACCEPT
$IPT -I FORWARD 1 -i $WG2_FACE -o $WG1_FACE -j ACCEPT
$IPT -I FORWARD 1 -i $WG1_FACE -o $WG2_FACE -j ACCEPT
```

Аналогічно для wg3 і на work-node (з їхніми SUB_NET та інтерфейсами). Важливо: у add-скриптах для wg2/wg3 потрібно мати змінні/інтерфейси для wg0 та wg1, щоб не дублювати логіку в багатьох місцях. Альтернатива — один окремий скрипт «повний mesh», що виконується після підняття всіх wg0–wg3.

## 3. Інші зауваження

### 3.1 Змінна SUB_NET у wg2/wg3

У **add-nat-routing-wg2.sh** і **add-nat-routing-wg3.sh** задано `SUB_NET`, але в правилах вона **не використовується** (немає MASQUERADE для цих підмереж). Це мертвий код. Або прибрати змінну, або залишити на майбутнє, якщо з’явиться NAT для wg2/wg3.

### 3.2 IPv6 (IPT6)

У всіх скриптах є `IPT6="/sbin/ip6tables"`, але він **ніде не використовується**. Якщо WireGuard або мережа працює з IPv6, потрібні відповідні правила в ip6tables; інакше можна прибрати IPT6, щоб не плутати.

### 3.3 Порядок вставки правил (-I 1)

Усі правила додаються через `-I ... 1`, тобто «на початок» ланцюга. Порядок підняття інтерфейсів (wg0 → wg1 → wg2 → wg3) визначає, які правила будуть вище. Для ACCEPT і для MASQUERADE з конкретними `-s SUB_NET` це зазвичай прийнятно. Якщо з’являться складніші правила (наприклад, обмеження по портах), варто перевірити, що порядок не ламає логіку.

### 3.4 PostDown / remove-скрипти

Ви не надали вміст **remove-nat-routing-wg*.sh**. Вони повинні **симетрично видаляти** ті самі правила, які додають add-скрипти (включаючи нові FORWARD wg0/wg1↔wg2/wg3, якщо їх додасте). Використовуйте `-D` з тими самими параметрами, що й `-I` (або нумерацію правил), інакше після `wg down` залишаться «сирі» правила і при наступному `wg up` будуть дублікати.

### 3.5 ip_forward

Щоб FORWARD працював, потрібно `net.ipv4.ip_forward=1`. У скриптах це не виставляється. Якщо це вже зроблено в системі (sysctl, systemd, тощо) — достатньо; інакше варто або додати в один із helper-скриптів, або гарантувати це окремо при налаштуванні хоста.

### 3.6 work-node wg3: закоментований MASQUERADE

У **add-nat-routing-wg3.sh** на work-node рядок NAT закоментований:  
`#$IPT -t nat -I POSTROUTING 1 -s $SUB_NET -o $IN_FACE -j MASQUERADE`  
Це узгоджується з тим, що для трафіку нод (wg2/wg3) NAT не робимо — помилкою не є.
