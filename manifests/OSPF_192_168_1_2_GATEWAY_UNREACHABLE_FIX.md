# Недоступність 192.168.1.1 та 192.168.2.1 між роутерами (Syhiv17 ↔ VRN625)

**Роутери:** VRN625 та Syhiv17 — це **Ubiquiti UniFi Cloud Gateway (UCG)**. OSPF на них керується через UniFi (FRR під капотом); vtysh доступний по SSH.

**Симптом:** з VRN625 `ping 192.168.1.1` не проходить, `ping 192.168.1.19` — проходить. З Syhiv17 `ping 192.168.2.1` не проходить, `ping 192.168.2.19` — проходить. Тобто **шлюзи (.1) недоступні**, а **хости за шлюзами (.19) доступні**.

### Результат перевірки rp_filter на UCG (актуально)

На **обох** UCG (Vernadskogo25 та Syhiv17-25) виведено:

- `net.ipv4.conf.all.rp_filter = 0`
- `net.ipv4.conf.default.rp_filter = 2`
- `net.ipv4.conf.wgclt1.rp_filter = 2`
- `net.ipv4.conf.wgclt2.rp_filter = 2`
- `net.ipv4.conf.br0.rp_filter = 2`

**Висновок:** rp_filter уже послаблений (0 для `all`, 2 для WG і br0), тому **причина недоступності .1 не в reverse path filter**.

### Причина знайдена: firewall UBIOS — WAN → LOCAL (INPUT)

На обох UCG трафік з інтерфейсів **wgclt1/wgclt2** зараховується до зони **WAN**. Вхідний трафік **до самого роутера** (destination = 192.168.1.1 або 192.168.2.1) потрапляє в ланцюг **INPUT → UBIOS_INPUT_USER_HOOK → wgclt+ → UBIOS_WAN_LOCAL_USER**.

У **UBIOS_WAN_LOCAL_USER** політика така:
- **ACCEPT** — якщо джерело в **UBIOS_policy_src_ip_1** (whitelist «дозволені джерела з WAN до шлюза»);
- **ACCEPT** — ctstate RELATED,ESTABLISHED;
- **DROP** — ctstate INVALID;
- для **state NEW**, що не пройшли перше правило — **NFLOG**, потім **DROP**.

На **Syhiv17** лічильник останнього DROP: **99817** пакетів; на **VRN625** — **5999** пакетів. Тобто **новий** трафік до адреси шлюза (.1), що приходить з WireGuard, **відкидається**, бо його джерело не входить у **UBIOS_policy_src_ip_1**.

**Висновок:** потрібно в UniFi додати до політики «дозволені джерела з WAN до шлюза» (або аналог — правило, що заповнює **UBIOS_policy_src_ip_1**) мережі WireGuard та інший LAN: **192.168.100.0/24**, **192.168.200.0/24**, **192.168.1.0/24**, **192.168.2.0/24**. Детально — розділ **3.1** нижче.

### Зв’язок із маршрутами з двома next hop (ECMP)

У таблиці OSPF на VRN625 та Syhiv17 частина маршрутів має **два next hop** (ECMP), наприклад:

- **VRN625:** 192.168.1.0/24 via 192.168.100.5 і via 192.168.200.5; 192.168.100.2/32, 192.168.200.2/32 — так само з двома via.
- **Syhiv17:** 192.168.2.0/24 via 192.168.100.1 і via 192.168.200.1; 192.168.100.6/32, 192.168.200.6/32 — з двома via.

Усі **недоступні** з VRN625 адреси (192.168.1.1, 192.168.100.2, 192.168.200.2) — це **локальні адреси Syhiv17** (br0 та wgclt1/wgclt2). Аналогічно з Syhiv17 недоступні 192.168.2.1, 192.168.100.6, 192.168.200.6 — локальні на VRN625. Тобто проблема не в тому, що маршрут має два next hop, а в тому, що **призначенням є інший роутер** (його .1 або WG-інтерфейси), і трафік **до цих адрес** при приході з WireGuard відкидається firewall (UBIOS_WAN_LOCAL_USER) на приймаючому UCG. Після виправлення правил WAN/VPN → Gateway (розділ 3.1) ці маршрути, включно з ECMP, мають стати доступними. Зміна cost в OSPF, щоб залишити один next hop, **не** усуває причину — потрібно саме дозволити вхід до шлюза з відповідних джерел.

## 1. Можлива причина: rp_filter (на UCG уже виключено)

- Трафік до **192.168.1.1** йде: VRN625 → Amper → Syhiv17. Пакет приходить на **Syhiv17 на інтерфейс wgclt1 або wgclt2**, а не на br0, де «живе» 192.168.1.1.
- Аналогічно трафік до **192.168.2.1** приходить на **VRN625 на wgclt1/wgclt2**, а не на br0.

Тобто пакет з адресою призначення «наш LAN‑шлюз» приходить з WireGuard, а ядро Linux перевіряє **reverse path (rp_filter)**. Якщо увімкнений **strict rp_filter** (значення 1), ядро перевіряє: «чи вийшов би відповідний трафік до джерела цього пакета саме з того інтерфейсу, на який він прийшов?» Через ECMP до 192.168.1.0/24 та 192.168.2.0/24 маршрут «назад» може бути через **інший** WG‑інтерфейс (wgclt1 vs wgclt2). Якщо пакет прийшов на wgclt1, а обраний маршрут до джерела — через wgclt2, пакет відкидається. Для трафіку до **.19** пакет часто проходить (forward на br0), тому що вже не є «локальним» для роутера і/або проходить інший шлях перевірки.

На реальних UCG перевірка показала, що rp_filter уже не strict (див. блок вище), тому ця гіпотеза не підтвердилась.

---

## 2. Якщо rp_filter був би причиною (на UCG уже не потрібно)

На **Syhiv17** та **VRN625** (Ubiquiti UCG) потрібно дозволити прийом трафіку до власних адрес (.1), навіть коли він приходить з WG, а не з br0. Найпростіше — послабити reverse path filter для відповідних інтерфейсів.

**Важливо для UCG:** на UniFi Cloud Gateway немає налаштування rp_filter через веб‑інтерфейс. Потрібен **SSH** на пристрій (увімкнути в UniFi Network Application: Settings → System → SSH Authentication). Після змін через `sysctl` перевірте, чи значення зберігаються після перезавантаження — на частині прошивок UCG файли в `/etc/sysctl.d/` можуть застосовуватися, але можуть і перезаписуватися оновленням. Якщо після ребуту проблема повертається — доведеться повторно застосувати або шукати офіційний спосіб збереження (custom config / script) для вашої версії UCG.

### 2.1 Перевірка поточного стану

На кожному роутері (Syhiv17, VRN625):

```bash
# Значення по інтерфейсах та за замовчуванням
sysctl -a 2>/dev/null | grep 'net.ipv4.conf.*\.rp_filter'
```

Якщо бачите `rp_filter = 1` для `wgclt1`, `wgclt2` або `all`/`default` — це може бути причиною.

### 2.2 Вимкнення strict rp_filter для WG та br0 (тимчасово)

На **обох** роутерах (Syhiv17 і VRN625):

```bash
# Loose mode (2) — приймати, якщо існує будь-який маршрут до джерела (рекомендовано)
sudo sysctl -w net.ipv4.conf.all.rp_filter=2
sudo sysctl -w net.ipv4.conf.default.rp_filter=2
sudo sysctl -w net.ipv4.conf.wgclt1.rp_filter=2
sudo sysctl -w net.ipv4.conf.wgclt2.rp_filter=2
sudo sysctl -w net.ipv4.conf.br0.rp_filter=2
```

Або повне вимкнення (0), якщо платформа не підтримує 2:

```bash
sudo sysctl -w net.ipv4.conf.all.rp_filter=0
sudo sysctl -w net.ipv4.conf.default.rp_filter=0
sudo sysctl -w net.ipv4.conf.wgclt1.rp_filter=0
sudo sysctl -w net.ipv4.conf.wgclt2.rp_filter=0
sudo sysctl -w net.ipv4.conf.br0.rp_filter=0
```

Після цього перевірити:

- З VRN625: `ping 192.168.1.1`
- З Syhiv17: `ping 192.168.2.1`

### 2.3 Постійне застосування

Додати у конфіг, який застосовується при завантаженні (наприклад, у **systemd** або **/etc/sysctl.d/**).

**Варіант A — файл в /etc/sysctl.d/ (рекомендовано):**

На **Syhiv17** і **VRN625** створити файл, наприклад `/etc/sysctl.d/99-ospf-wg-rpfilter.conf`:

```conf
# Дозволити прийом трафіку до локальних адрес (.1), що приходить з WG (для OSPF mesh)
net.ipv4.conf.all.rp_filter=2
net.ipv4.conf.default.rp_filter=2
net.ipv4.conf.wgclt1.rp_filter=2
net.ipv4.conf.wgclt2.rp_filter=2
net.ipv4.conf.br0.rp_filter=2
```

Застосувати без перезавантаження:

```bash
sudo sysctl -p /etc/sysctl.d/99-ospf-wg-rpfilter.conf
```

**Варіант B — тільки для WG-інтерфейсів:**

Якщо не хочете змінювати rp_filter для всього хоста, можна обмежитися лише інтерфейсами WireGuard (на обох роутерах імена можуть відрізнятися):

```conf
net.ipv4.conf.wgclt1.rp_filter=2
net.ipv4.conf.wgclt2.rp_filter=2
```

Після змін перезавантаження не обов’язкове; достатньо `sysctl -p` для обраного файлу.

**На UCG:** якщо через SSH немає доступу до `sudo` або до `/etc/sysctl.d/`, спробуйте тільки тимчасові `sysctl -w` — після перезавантаження налаштування зникнуть, але можна перевірити, що саме rp_filter був причиною. Далі варто переглянути офіційну документацію Ubiquiti щодо custom sysctl або збереження параметрів ядра на UCG.

## 3. Firewall (INPUT) на UCG — причина підтверджена (UBIOS_WAN_LOCAL_USER)

Трафік до .1 відкидається ланцюгом **UBIOS_WAN_LOCAL_USER**: з WAN (в т.ч. wgclt1/wgclt2) до «Local» (шлюз) дозволений лише трафік з джерел із **UBIOS_policy_src_ip_1**; решта **state NEW** — DROP.

### 3.1 Що зробити в UniFi Network Application

Потрібно **розширити whitelist джерел, яким дозволено звертатися до шлюза з WAN**. Це зазвичай налаштовується правилом типу «Allow access to Gateway» / «Allow WAN → Local» з обмеженням по Source. Джерела мають включати:

| Мережа / джерело | Призначення |
|------------------|-------------|
| **192.168.100.0/24** | WireGuard (Amper master, Syhiv17 wgclt1, VRN625 wgclt1) |
| **192.168.200.0/24** | WireGuard (Amper worker, Syhiv17 wgclt2, VRN625 wgclt2) |
| **192.168.1.0/24** | LAN Syhiv17 — щоб з VRN625/Amper пинг до 192.168.1.1 проходив, якщо джерело вже перетворене або якщо пинг йде з 192.168.1.x |
| **192.168.2.0/24** | LAN VRN625 — аналогічно для доступу до 192.168.2.1 |

**Де шукати в UniFi:**  
Settings → Firewall & Security → Firewall Rules (або Traffic Rules), правило, що дозволяє доступ **до Device / Gateway** з **WAN** (або з певних мереж). Там має бути можливість вказати **Source** (або «Allowed IPs»). Додайте мережі вище до джерел, яким дозволено звертатися до шлюза. Якщо такого окремого правила немає і є лише загальна політика «WAN → Local: drop new», створіть правило **Allow**, зона джерела — WAN (або інтерфейс/мережа WireGuard), destination — Device/Gateway, Source — 192.168.100.0/24, 192.168.200.0/24, 192.168.1.0/24, 192.168.2.0/24.

Після збереження і застосування правил перевірте знову: з VRN625 `ping 192.168.1.1`, з Syhiv17 `ping 192.168.2.1`. Лічильник DROP у **UBIOS_WAN_LOCAL_USER** на відповідному роутері перестане зростати для цих пингів.

**Важливо:** правило типу «Oracle Cloud to Gateway» з Src. Zone = **External** застосовується лише до трафіку, який прийшов у зоні **External**. Якщо інтерфейси **wgclt1/wgclt2** у UniFi прив’язані до зони **VPN** (а не External), то трафік з WireGuard йде як **VPN → Gateway** і це правило не спрацьовує — тоді потрібно додати окреме правило VPN → Gateway з тими ж 8 subnets (див. попередній абзац). Якщо ж до зони **External** прив’язані мережі/інтерфейси **Amper Master** та **Amper Worker** (як на знімку Zone Definition), то трафік з wgclt вже йде як External, і «Oracle Cloud to Gateway» має застосовуватися. Якщо пінги до .1 досі не проходять — перевірте **на другому UCG (Syhiv17)** ту саму таблицю Zone Name / Networks: чи там теж Amper Master і Amper Worker в зоні External і чи є правило Allow до Gateway з тими ж 8 subnets. На обох роутерах має бути узгоджена конфігурація.

### 3.2 Перевірка по iptables (опційно)

На UCG по SSH можна переконатися, що трафік до .1 йде саме в UBIOS_WAN_LOCAL_USER і там дропається:

```bash
iptables -L INPUT -n -v
# далі: iptables -L UBIOS_INPUT_JUMP -n -v, UBIOS_INPUT_USER_HOOK -n -v, UBIOS_WAN_LOCAL_USER -n -v
```

Перед виправленням у UBIOS_WAN_LOCAL_USER буде правило з DROP і лічильник (pkts) буде зростати при пингу до .1 з іншого боку.

## 4. Довгостроково: оголошувати лише /32 (опційно)

У **OSPF_ROUTERS_HOST_ROUTES_32.md** описано підхід: **не** оголошувати в OSPF мережі 192.168.1.0/24 та 192.168.2.0/24, а тільки потрібні хост-маршрути (/32). Перехід на /32 покращує передбачуваність маршрутизації; на недоступність .1 це може не вплинути, якщо причина в firewall.

| Крок | Дія |
|-----|-----|
| 1 | Перевірити rp_filter — **виконано**: на UCG вже all=0, wgclt/br0=2. |

## 6. Далі діагностика (якщо .1 досі недоступні)

Оскільки rp_filter на UCG не є причиною, варто перевірити, чи пакети взагалі доходять до роутера і чи йде reply.

**На роутері, куди летить ping (наприклад, Syhiv17 при ping 192.168.1.1 з VRN625):**

```bash
# Запустити на Syhiv17 перед пингом з VRN625 до 192.168.1.1
tcpdump -i wgclt1 -n host 192.168.1.1
# або обидва WG: tcpdump -i any -n host 192.168.1.1
```

- Якщо **бачите вхідні ICMP request** і **немає ICMP reply** — пакет прийшов, але відповідь не виходить: ймовірно firewall (INPUT або політика для інтерфейсу) або щось інше на рівні ядра/UniFi.
- Якщо **немає вхідних request** — трафік не доходить (маршрутизація на Amper або на VRN625, або дроп раніше по шляху).

**Перевірка правил на UCG по SSH:**

```bash
iptables -L INPUT -n -v
iptables -L -n -v   # всі ланцюги
nft list ruleset 2>/dev/null || true
```

Шукайте правила, що DROP або REJECT трафік до 192.168.1.1 / 192.168.2.1 або з джерел 192.168.100.0/24, 192.168.200.0/24. Якщо такі є і вони від UniFi (зона guest/VPN тощо) — додайте виключення в UniFi Network Application або з’ясуйте, чи можна дозволити доступ до шлюза з цих мереж.

## 7. Правила вже дозволені, але пінг не йде — чеклист

Якщо на **обох** UCG (Syhiv17 та Vernadskogo25) ви додали правило типу «Oracle Cloud to Gateway» (External → Gateway, джерела 8 subnets), а пінг до .1 і до WG-адрес (192.168.100.2, 192.168.200.2 тощо) все одно не проходить, перевірте по пунктах.

### 7.1 Порядок правил (пріоритет)

У UniFi зазвичай **перше збігле правило** застосовується. Якщо для пари зон **External → Gateway** є:
- спочатку правило **Block** (наприклад «Block Invalid Traffic» або «Block All Traffic»),
- а потім **Allow** («Oracle Cloud to Gateway»),

то блок спрацює раніше і трафік буде відкинуто. Потрібно, щоб правило **Allow** для External → Gateway з джерелами 192.168.x.x мало **менший ID** (було вище в списку), ніж будь-яке **Block** для External → Gateway. Перетягніть правило Allow вище або змініть порядок так, щоб воно оброблялося першим.

### 7.2 На обох роутерах має бути правило External → Gateway

- **Syhiv17:** потрібно правило **External → Gateway**, Allow, Src. = 192.168.100.0/24, 192.168.200.0/24, 192.168.1.0/24, 192.168.2.0/24 (або еквівалентні 8 subnets). Воно дозволяє трафік **до Syhiv17** (192.168.1.1, 192.168.100.2, 192.168.200.2), коли пакети приходять з wgclt (External).
- **Vernadskogo25:** аналогічно потрібно правило **External → Gateway**, Allow, ті самі джерела. Правило типу «Syhiv transyt» (Internal → External) стосується **транзитного** трафіку з LAN у зовнішні мережі; воно **не** дозволяє трафік **до самого роутера** (192.168.2.1, 192.168.100.6, 192.168.200.6) з інтерфейсів wgclt. Тому на VRN625 має бути окреме правило саме **External → Gateway** з джерелами Oracle/OSPF (8 subnets), як на Syhiv17.

Переконайтеся, що на **Vernadskogo25** є правило з Dst. Zone = **Gateway** і Src. Zone = **External** (а не лише Internal → External).

### 7.3 Джерела (Src.) мають покривати реальний source ping

Коли з VRN625 виконується `ping 192.168.1.1`, джерело пакета — одна з адрес VRN625 (наприклад 192.168.100.6 або 192.168.200.6, рідше 192.168.2.1). У правилі Allow для Gateway на **Syhiv17** у полі Src. мають бути мережі, що включають ці адреси: 192.168.100.0/24 (або мінімум 192.168.100.4/30, 192.168.100.0/30), 192.168.200.0/24 (або 192.168.200.4/30, 192.168.200.0/30), 192.168.2.0/24. Аналогічно на VRN625 для пингів з Syhiv17 — 192.168.1.0/24, 192.168.100.x, 192.168.200.x. Якщо в правилі вказані лише окремі /30 або «+3» адреси — перевірте, що туди входять усі потрібні діапазони.

### 7.4 Зона інтерфейсів wgclt

Якщо **Amper Master** і **Amper Worker** на роутері прив’язані до зони **External**, трафік з wgclt обробляється як External. Якщо вони в зоні **VPN** (або іншій), то правило з Src. Zone = External не застосується; потрібно окреме правило **VPN → Gateway** (або відповідна зона) з тими ж джерелами.

### 7.5 Діагностика: tcpdump та лічильники iptables

На **Syhiv17** (під час пингу з VRN625 до 192.168.1.1):

```bash
tcpdump -i any -n 'icmp and host 192.168.1.1'
```

- Якщо **немає вхідних пакетів** — трафік не доходить до Syhiv17 (проблема на VRN625, Amper або маршрутизації).
- Якщо **є вхідні request, немає reply** — пакет прийшов, але відповідь блокується або не відправляється (firewall OUTPUT або політика для інтерфейсу, або правило Allow все ще не перше для цієї пари зон).

Після кількох пингів перевірте по SSH лічильник DROP у UBIOS_WAN_LOCAL_USER:

```bash
iptables -L UBIOS_WAN_LOCAL_USER -n -v
```

Якщо лічильник **DROP** зростає при кожному пингу — правило Allow не спрацьовує (порядок, зона або джерело не збігаються). Після коректного виправлення цей лічильник для нового трафіку до .1 зростати не повинен.

## 8. Асиметричний шлях: request на wgclt1, reply виходить на wgclt2

Якщо на роутері, куди летить пінг (наприклад Syhiv17), **tcpdump** показує і вхідний request, і вихідний reply, але на стороні відправника (VRN625) пінг усе одно не проходить, причина — **асиметричний повернення reply**.

**Приклад з tcpdump на Syhiv17** (ping з VRN625 до 192.168.1.1):
- **In:** request приходить на **wgclt1** (192.168.100.6 → 192.168.1.1).
- **Out:** reply виходить на **wgclt2** (192.168.1.1 → 192.168.100.6).

Тобто reply йде з Syhiv17 через **інший** інтерфейс (wgclt2), ніж той, куди прийшов request (wgclt1). Через ECMP маршрут з Syhiv17 до 192.168.100.6 має два next hop (via 192.168.100.1 і via 192.168.200.1), і ядро обирає wgclt2 для reply. Reply потрапляє на VRN625 на **wgclt2**, тоді як вихідний request пішов з VRN625 через **wgclt1**. Connection tracking на VRN625 може позначити такий reply як **INVALID** (відповідь прийшла на «неправильний» інтерфейс), і правило **Block Invalid Traffic** його відкидає — тому пінг не проходить, хоча Syhiv17 reply реально відправляє.

### 8.1 Виправлення: симетричний маршрут для reply

Потрібно, щоб reply з Syhiv17 до 192.168.100.6 виходив через **wgclt1** (той самий інтерфейс, куди прийшов request). Тоді reply прийде на VRN625 на wgclt1, і conntrack прийме його як коректний return traffic.

**Спосіб:** змінити OSPF cost так, щоб з Syhiv17 мережа **192.168.100.0/24** (зокрема 192.168.100.6) була досяжна лише через **wgclt1**, а 192.168.200.0/24 — через wgclt2. Наприклад, на **Syhiv17** встановити вищий cost на інтерфейсі **wgclt2** для OSPF, щоб маршрути до 192.168.100.x йшли лише через wgclt1 (next hop 192.168.100.1). Аналогічно на **VRN625**: переконатися, що до 192.168.100.x трафік йде через wgclt1, до 192.168.200.x — через wgclt2, щоб відповіді поверталися тим самим інтерфейсом.

**Приклад на Syhiv17 (vtysh):**
```text
configure terminal
interface wgclt2
 ip ospf cost 50
exit
write memory
```
(Значення cost для wgclt1 залишити 10 або за замовчуванням; 50 зробить шлях через wgclt2 до 192.168.100.x гіршим, і reply до 192.168.100.6 піде через wgclt1.)

Після зміни перевірити: з VRN625 `ping 192.168.1.1` має проходити; на Syhiv17 у tcpdump reply має виходити на **wgclt1**, а не wgclt2.

**На VRN625** для симетрії в зворотному напрямку (ping з Syhiv17 до 192.168.2.1) можна аналогічно задати вищий cost на одному з wgclt, щоб reply до Syhiv17 (192.168.100.2 або 192.168.200.2) повертався тим інтерфейсом, на який прийшов request.

**Failover:** після зміни cost у таблиці маршрутів залишається один next-hop (наприклад усі через wgclt1). Коли цей тунель або сусід OSPF по ньому перейде в down, OSPF перерахує маршрути, і трафік перейде на інший тунель (wgclt2). Після відновлення лінку знову буде обрано кращий шлях (нижчий cost). Тобто симетрія не заважає автоматичному перемиканню на резервний тунель.

### 8.2 Якщо після cost 10.0.10.20 став недоступний (тільки 10.0.10.10 працює)

**10.0.10.10** — Amper master, **10.0.10.20** — Amper worker. Вони досяжні лише через «свій» тунель: master — через wgclt1 (192.168.100.5), worker — через wgclt2 (192.168.200.5). Якщо на **VRN625** так само підвищити cost на wgclt2, усі маршрути підуть через wgclt1; тоді трафік до **10.0.10.20** піде на master (192.168.100.5), а не на worker, і worker стає недоступним.

**Що зробити:** зміну cost застосовувати **тільки на тому роутері, де потрібна симетрія для reply**. Для пингу з VRN625 до 192.168.1.1 reply має виходити з Syhiv17 через wgclt1 — тому вищий cost на **wgclt2 достатньо лише на Syhiv17**. На **VRN625** cost на wgclt2 **не підвищувати** (або повернути до попереднього), щоб 10.0.10.20 залишався через wgclt2 (192.168.200.5).

**Підсумок:**
- **Syhiv17:** залишити вищий cost на wgclt2 → reply до 192.168.100.6 йде через wgclt1, пінг з VRN625 до 192.168.1.1 працює.
- **VRN625:** cost на обох wgclt однаковий (або нижчий на wgclt2 для мереж від worker) → 10.0.10.10 via wgclt1, 10.0.10.20 via wgclt2, обидва Amper-хости доступні. Пінг з Syhiv17 до 192.168.2.1 при ECMP може залишатися з асиметрією; якщо він потрібен, можна окремо розглянути policy routing або виключення для ICMP у Block Invalid на VRN625.
