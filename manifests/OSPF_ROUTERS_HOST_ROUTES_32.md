# OSPF: оголошувати лише /32 (хости), не /24

Мережі **192.168.1.0/24** та **192.168.2.0/24** в OSPF **не** оголошуються ні роутерами, ні хостами кластера. Оголошуються лише конкретні хости /32.

## Роутери VRN625 та Syhiv17

| Роутер | Замість | Оголошувати в OSPF |
|--------|---------|---------------------|
| **Syhiv17** | 192.168.1.0/24 | **192.168.1.1/32** (сам роутер) |
| **VRN625** | 192.168.2.0/24 | **192.168.2.1/32**, **192.168.2.31/32**, **192.168.2.198/32** |

## Хости macmini7 та beelinkeqr5

**Зараз** macmini7 та beelinkeqr5 **не беруть участі в OSPF** — вони підключені до роутерів Syhiv17 та VRN625, які забезпечують маршрутизацію до них. Якщо колись ці хости увійдуть в OSPF, вони так само **не** повинні оголошувати мережі 192.168.1.0/24 та 192.168.2.0/24, лише свої хост-маршрути /32:

| Хост | Замість | Оголошувати в OSPF |
|------|---------|---------------------|
| **macmini7** (VRN625, 192.168.2.19) | 192.168.2.0/24 | **192.168.2.19/32** |
| **beelinkeqr5** (Syhiv17, 192.168.1.19) | 192.168.1.0/24 | **192.168.1.19/32** |

Приклади конфігурації FRR для macmini7 та beelinkeqr5 — у **FRR_OSPF_CONFIG_EXAMPLES.md** (розділи 3.3 та 3.4).

Інтерфейси WireGuard (192.168.100.x, 192.168.200.x) залишаються в OSPF як раніше.

---

## 1. Ідея рішення

- **Прибрати** з OSPF оголошення мережі LAN (`network 192.168.1.0/24` / `network 192.168.2.0/24`).
- **Додати** в OSPF лише маршрути до потрібних /32:
  - **Syhiv17:** один хост — 192.168.1.1/32 (адреса роутера).
  - **VRN625:** три хости — 192.168.2.1/32 (роутер), 192.168.2.31/32, 192.168.2.198/32.
  - **macmini7:** один хост — 192.168.2.19/32 (не 192.168.2.0/24).
  - **beelinkeqr5:** один хост — 192.168.1.19/32 (не 192.168.1.0/24).

Реалізація залежить від платформи: **FRR** (vtysh) або **UniFi UI**.

---

## 2. FRR (vtysh) — два варіанти

### 2.1 Варіант A: loopback + `network` для /32

**Syhiv17**

- На loopback (або dummy) додати адресу **192.168.1.1/32** (якщо вона вже є на LAN як 192.168.1.1/24, на lo можна додати той самий /32 для OSPF).
- У OSPF: **прибрати** `network 192.168.1.0/24 area 0`, **додати** `network 192.168.1.1/32 area 0`.
- Інтерфейс LAN у OSPF **не** включати (щоб /24 не потрапляло в LSA).

**VRN625**

- Для 192.168.2.1/32 — аналогічно: 192.168.2.1/32 на loopback, в OSPF тільки `network 192.168.2.1/32 area 0`.
- Для 192.168.2.31/32 та 192.168.2.198/32 — це інші хости в мережі; їх **не** додавати на lo. Замість цього:
  - задати **статичні маршрути** до цих хостів через LAN-інтерфейс (наприклад `ip route 192.168.2.31/32 br0`, `ip route 192.168.2.198/32 br0`);
  - у FRR: **redistribute static** в OSPF з **route-map**, який дозволяє лише ці /32.

Нижче — варіант B без loopback для 192.168.2.31 та 192.168.2.198: тільки static + redistribute.

### 2.2 Варіант B: static + redistribute з route-map (рекомендовано для VRN625)

На **VRN625** (якщо є доступ до vtysh / FRR):

1. **Статичні маршрути** до хостів (ім’я інтерфейсу LAN — наприклад `br0` або `eth1` підставити самому):

```bash
# На роутері (Linux/FRR)
sudo ip route add 192.168.2.31/32 dev br0    # або via 192.168.2.31
sudo ip route add 192.168.2.198/32 dev br0   # або via 192.168.2.198
```

Для 192.168.2.1/32 маршрут уже є (connected на LAN). Щоб його оголошувати в OSPF окремо від /24, зручно мати **192.168.2.1/32 на loopback** і в OSPF включити лише цей /32 (див. конфіг нижче).

2. **Prefix-list** — дозволити лише потрібні /32:

```vtysh
ip prefix-list ROUTERS-HOSTS seq 5 permit 192.168.2.1/32
ip prefix-list ROUTERS-HOSTS seq 10 permit 192.168.2.31/32
ip prefix-list ROUTERS-HOSTS seq 15 permit 192.168.2.198/32
```

3. **Route-map** для redistribute:

```vtysh
route-map REDIST-ONLY-32 permit 10
 match ip address prefix-list ROUTERS-HOSTS
```

4. **OSPF:** прибрати `network 192.168.2.0/24 area 0`, додати redistribute static + connected через цей route-map:

```vtysh
router ospf
 no network 192.168.2.0/24 area 0.0.0.0
 redistribute static route-map REDIST-ONLY-32
 redistribute connected route-map REDIST-ONLY-32
```

Щоб у OSPF потрапляв саме 192.168.2.1/32, а не 192.168.2.0/24 з LAN, варіанти:

- **А)** Не включати LAN-інтерфейс в OSPF (`network 192.168.2.0/24` прибрати), а 192.168.2.1/32 отримати з **loopback** (додати на lo адресу 192.168.2.1/32 і в prefix-list дозволити тільки цей /32), або  
- **Б)** Залишити redistribute connected з route-map REDIST-ONLY-32 — тоді з connected піде лише те, що збігається з prefix-list (у FRR match по prefix-list обмежує, які connected/static маршрути редистрибутуються). Перевірити: чи FRR при redistribute connected відфільтрує 192.168.2.0/24 і залишить тільки 192.168.2.1/32, залежить від того, як згенерований connected — часто є і /24, і /32 для адреси інтерфейсу. Тому надійніше для 192.168.2.1/32 використати loopback і не включати 192.168.2.0/24 в OSPF взагалі.

Нижче — зведений приклад конфігу для обох роутерів у стилі «тільки /32».

## 3. Зведені приклади конфігурації FRR

### 3.1 Syhiv17 — оголошувати лише 192.168.1.1/32

- На **loopback** додати `192.168.1.1/32` (якщо ще немає).
- У OSPF **прибрати** `network 192.168.1.0/24 area 0`.
- **Додати** `network 192.168.1.1/32 area 0`.
- LAN-інтерфейс (192.168.1.0/24) в OSPF **не** включати.

```vtysh
configure terminal
! На Syhiv17: loopback з 192.168.1.1/32 (якщо платформа дозволяє — інтерфейс lo)
interface lo
 ip address 192.168.1.1/32
exit
router ospf
 router-id 0.0.0.4
 no network 192.168.1.0/24 area 0.0.0.0
 network 192.168.1.1/32 area 0.0.0.0
 network 192.168.100.0/24 area 0.0.0.0
 network 192.168.200.0/24 area 0.0.0.0
 passive-interface default
 no passive-interface wgclt1
 no passive-interface wgclt2
exit
write memory
exit
```

Якщо на Syhiv17 вже є 192.168.1.1/24 на LAN і не можна використати той самий IP на lo, можна замість цього: **не** оголошувати 192.168.1.0/24 в OSPF і редистрибувати **connected** з route-map, що дозволяє лише 192.168.1.1/32 (тоді в prefix-list один permit 192.168.1.1/32).

### 3.2 VRN625 — оголошувати лише 192.168.2.1/32, 192.168.2.31/32, 192.168.2.198/32

- **Прибрати** з OSPF: `network 192.168.2.0/24 area 0`.
- Додати **статичні** маршрути для 192.168.2.31/32 та 192.168.2.198/32 (через LAN-інтерфейс).
- Для 192.168.2.1/32: або loopback з 192.168.2.1/32 + `network 192.168.2.1/32 area 0`, або redistribute connected з route-map (лише 192.168.2.1/32).
- Редистрибуція **static** (і за потреби **connected**) через route-map, що дозволяє лише ці три /32.

**Prefix-list і route-map:**

```vtysh
ip prefix-list ROUTERS-HOSTS seq 5 permit 192.168.2.1/32
ip prefix-list ROUTERS-HOSTS seq 10 permit 192.168.2.31/32
ip prefix-list ROUTERS-HOSTS seq 15 permit 192.168.2.198/32
!
route-map REDIST-ONLY-32 permit 10
 match ip address prefix-list ROUTERS-HOSTS
```

**Статичні маршрути** (на Linux, ім’я інтерфейсу — за фактом):

```bash
ip route add 192.168.2.31/32 dev br0
ip route add 192.168.2.198/32 dev br0
```

**OSPF (vtysh):**

```vtysh
router ospf
 router-id 0.0.0.3
 no network 192.168.2.0/24 area 0.0.0.0
 network 192.168.100.0/24 area 0.0.0.0
 network 192.168.200.0/24 area 0.0.0.0
 redistribute static route-map REDIST-ONLY-32
 redistribute connected route-map REDIST-ONLY-32
 passive-interface default
 no passive-interface wgclt1
 no passive-interface wgclt2
exit
```

Якщо при `redistribute connected` у OSPF все одно потрапляє 192.168.2.0/24 (через connected на LAN), тоді LAN **не** включати в OSPF і 192.168.2.1/32 отримувати з **loopback**: додати на lo `192.168.2.1/32` і в prefix-list залишити три permit для 192.168.2.1/32, 192.168.2.31/32, 192.168.2.198/32; static редистрибувати як вище.

## 4. UniFi (UCG) — обмеження UI

У **UniFi Network Application** (OSPF) зазвичай можна вибрати лише **інтерфейси** або **мережі** типу 192.168.1.0/24, без тонкого контролю «тільки /32». Тому:

- Якщо на VRN625/Syhiv17 працює **UniFi**, а не «голий» FRR, варіанти:
  - Шукати в UI опції на кшталт **Custom networks** / **Prefix list** / **Redistribute only specific routes** і задати лише 192.168.1.1/32, 192.168.2.1/32, 192.168.2.31/32, 192.168.2.198/32, якщо такі є.
  - Якщо є доступ по SSH до UCG і там встановлено FRR — змінити конфіг FRR вручну (як у розділах 2–3), зберігши його і перезапустивши FRR; потім перевірити, чи UniFi не перезаписує його при оновленні.
  - Якщо нічого з цього неможливо — залишити оголошення /24 і обмежити вплив на інших роутерах (наприклад, фільтром на прийом маршрутів на Amper/macmini/beelink), що менш ідеально.

## 5. Підсумок

| Роутер   | Що прибрати з OSPF   | Що оголошувати в OSPF |
|----------|----------------------|-------------------------|
| **Syhiv17** | 192.168.1.0/24       | 192.168.1.1/32          |
| **VRN625**  | 192.168.2.0/24       | 192.168.2.1/32, 192.168.2.31/32, 192.168.2.198/32 |

- WireGuard-мережі (192.168.100.0/24, 192.168.200.0/24) на обох роутерах у OSPF залишаються без змін.
- Реалізація: **FRR** — через `network` для /32 (з loopback де потрібно) та/або **redistribute static/connected** з **route-map** і **prefix-list**; **UniFi** — за можливостями UI або ручна правка FRR.
- **Недоступність .1 або WG-адрес (192.168.100.2, 192.168.200.2 тощо) між UCG** не пов’язана з типом маршруту (/24 vs /32) і не зникає після переходу на /32. Причина — firewall UBIOS (WAN/VPN → Gateway); виправлення — **OSPF_192_168_1_2_GATEWAY_UNREACHABLE_FIX.md** (дозволити джерела 192.168.100.0/24, 192.168.200.0/24, 192.168.1.0/24, 192.168.2.0/24 до шлюза в UniFi).
