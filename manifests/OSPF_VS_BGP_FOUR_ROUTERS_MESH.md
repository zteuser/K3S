# OSPF vs BGP для схеми з чотирьома роутерами та full-mesh WireGuard

**Контекст:** чотири вузли в OSPF — Amper master, Amper worker, Syhiv17 (UCG), VRN625 (UCG); full-mesh тунелів WG між Amper і двома UCG (master ↔ Syhiv17, master ↔ VRN625, worker ↔ Syhiv17, worker ↔ VRN625). Master і worker не мають прямого WG між собою, лише OCI (enp0s6).

---

## 1. Що вже виникло з OSPF

- **Firewall UBIOS:** трафік до шлюза (.1) з WG відкидався (WAN → Local), потрібні явні Allow-правила для 8 subnets.
- **Асиметричний reply:** при ECMP reply виходив іншим інтерфейсом, ніж request → conntrack INVALID → «Block Invalid Traffic» дропав пінг.
- **Ручне керування cost:** щоб reply йшов потрібним інтерфейсом, на Syhiv17 підняли cost на wgclt2; на VRN625 cost не чіпали, щоб 10.0.10.20 лишався через wgclt2. Логіка різна на двох роутерах, її треба пам’ятати при змінах.
- **Failover:** при down одного тунеля OSPF перераховує маршрути — це працює, але вибір шляху визначається лише cost інтерфейсу, без тонкого контролю «цей префікс тільки через цей peer».

---

## 2. Чому BGP може бути оптимальнішим і простішим

Для **чотирьох роутерів** і **full-mesh логіки** (кожен знає мережі всіх, але next-hop можна явно вибирати) BGP дає:

| Аспект | OSPF | BGP |
|--------|------|-----|
| **Вибір шляху** | За cost інтерфейсу; ECMP за однакового cost, next-hop «випадковий» | Явні політики: local-preference, MED, AS-path. Один обраний next-hop на префікс без несподіванок. |
| **Симметрія request/reply** | Доводиться добиватися cost (різна конфіг на Syhiv17 і VRN625) | Наприклад: на Syhiv17 приймати 192.168.100.6/32 з master з кращим local-pref — один next-hop через wgclt1. Reply завжди через wgclt1. |
| **10.0.10.10 vs 10.0.10.20** | Обидва через одного сусіда, якщо cost один — потрібні виключення (не піднімати cost на VRN625 wgclt2) | Master рекламує 10.0.10.10/32, worker — 10.0.10.20/32; next-hop = self. Кожен роутер природно має один шлях до кожного з них (через «свій» тунель). |
| **Конфіг на UCG** | OSPF + cost на інтерфейсах + розуміння, де cost не чіпати | BGP neighbor + import/export policy (prefix-list, route-map, local-pref). Один стиль політики на всіх. |
| **Failover** | Автоматично після dead timer, перерахунок дерева | Автоматично: при down сесії BGP withdraw маршрутів; інший peer лишається, маршрут від нього в таблиці. Таймери (keepalive/hold) можна зменшити для швидкої зміни. |
| **Розмір мережі** | OSPF добре підходить для великих внутрішніх мереж | BGP типовий для «мережі мереж», кілька сусідів, політики — як раз ваш випадок (4 вузли, кілька тунелів). |

Тобто при такій схемі BGP не складніший за OSPF з уже внесеними костами та виключеннями, а дає **передбачуваний один next-hop на префікс** і уникає проблем з ECMP/conntrack і різним cost на різних роутерах.

---

## 3. Що потрібно для переходу на BGP

- **Топологія сесій:** master — сесії з worker (enp0s6), Syhiv17 (wg0), VRN625 (wg1); worker — з master (enp0s6), Syhiv17 (wg0), VRN625 (wg1); Syhiv17 — з master (wgclt1), worker (wgclt2); VRN625 — з master (wgclt1), worker (wgclt2). Разом 5 пар (master–worker, master–Syhiv17, master–VRN625, worker–Syhiv17, worker–VRN625). Між Syhiv17 і VRN625 прямого лінку немає.
- **AS:** один приватний AS (наприклад 65001) для всіх або окремі AS на кожному вузлі — за бажанням; для внутрішнього mesh достатньо одного AS і local-pref/MED для вибору шляху.
- **Що рекламувати:** ті самі мережі, що й зараз в OSPF (10.0.10.10/32, 10.0.10.20/32, 192.168.1.0/24 або /32, 192.168.2.0/24 або /32, 192.168.100.x, 192.168.200.x). Next-hop self на кожному роутері для своїх connected.
- **Політики:** на UCG (Syhiv17, VRN625) import route-map: давати кращий local-pref маршрутам, отриманим від «потрібного» peer (наприклад до 192.168.100.6 — лише від master), щоб був один next-hop і симетричний шлях. На Amper — export connected у BGP; при потребі фільтр префіксів.
- **Підтримка:** FRR (bgpd) на Amper вже є; на UCG потрібно перевірити, чи UniFi/FRR дозволяє BGP і чи не перезатирає конфіг після оновлень. Якщо BGP на UCG підтримується — міграція реалістична.

---

## 4. Висновок

Для **даної схеми (4 роутери, full-mesh тунелів, потреба в симетричному шляху і чіткому доступу до 10.0.10.10 та 10.0.10.20)** перехід на **BGP** може бути **оптимальнішим і простішим у експлуатації**: один механізм вибору шляху (політики), без ECMP-відмінностей і ручних cost-виключень, з тим самим failover при падінні тунеля. Якщо UCG коректно підтримує BGP (включно з збереженням конфігу), варто розглянути міграцію; якщо залишатися на OSPF — поточна схема з різним cost лише на Syhiv17 і правилами firewall залишається валідним робочим варіантом.
